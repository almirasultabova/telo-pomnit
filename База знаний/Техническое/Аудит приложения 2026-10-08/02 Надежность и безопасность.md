## Вывод и порядок работ

Главный долг приложения — доверие к сохранению и приватности. Красивый экран «Сохранено» сейчас может появиться при несохранённой записи. После смены аккаунта локальные личные данные не разделены. Платёжный webhook действующего сервера доверяет входящему JSON без проверки у провайдера. Эти вещи следует исправлять раньше расширения AI, геймификации и сложных анимаций.

| Приоритет | Работа | Проверяемый результат |
|---|---|---|
| P0 | Защитить платёжный webhook | Поддельное уведомление не выдаёт paidAt; подтверждённое тестовое событие выдаёт права ровно один раз |
| P0 | Честное сохранение + outbox | При сбое виден черновик/ожидание; повторный вход сохраняет запись; повтор запроса не дублирует её |
| P0 | Разделить локальные данные аккаунтов | Новый аккаунт никогда не видит кэш, согласие и диагностику предыдущего |
| P1 | Сверить и выровнять production/local auth | Старые подписанные initData не восстанавливают сессию без конца; срок сессии осознанно задан |
| P1 | Приватность AI и право управлять своими данными | Видно, что передаётся AI; дневник можно исключить; экспорт/удаление доступны после отзыва допуска |
| P1 | Восстановление шкал чекина | Каждая шкала после входа равна исходной, график не подменяет пять ответов средним |
| P1 | Уведомления и календарь | Работают согласованные время/пауза, напоминания встречи; нет дублей из нескольких зачислений |
| P2 | Наблюдаемость, безопасный HTML, производительность | Ошибка различима; экран не раскрывает заметки в коде/логах; измерения на реальном Telegram |

P0/P1 — порядок продукта; severity ниже относится к доказанному security impact, а не равна приоритету UX.

## Подтверждённые находки

### S-01 — поддельный webhook способен назначить оплаченные права

**Production, security severity high, confidence high.** `output/app-audit-20261008/server/payment.js:84–115` принимает `payment.succeeded` и напрямую вызывает письмо/зачисление; `:152–156` выставляет `paidAt`. Здесь нет проверки IP, аутентификации, повторного GET статуса платежа у ЮKassa, суммы/валюты/покупки/принадлежности магазину. `server/nginx-api.conf:4–12` проксирует общий путь, отдельного allow/deny на webhook нет. Admission при этом остаётся независимым: поддельная оплата сама не открывает закрытое приложение. Но уже допущенный аккаунт получает оплаченные возможности без платежа, а внешний отправитель может инициировать письма и создавать pending-данные.

**Предусловие:** доступ к публичному маршруту webhook, имя Telegram-аккаунта для зачисления. **Безопасный repro:** `security-production-repro.cjs` загружает серверный source в VM, заменяет DB/email/bot заглушками и через Fastify.inject отправляет фиктивное событие; проверено создание зачисления с непроверенным ID. На production запрос не отправлялся. **Исправление:** webhook как сигнал; сервер получает объект платежа через API провайдера, проверяет succeeded/paid, shop, сумму, RUB, сохранённый order/stream/account, затем транзакционно проводит событие с уникальным paymentId. Письмо/уведомление только после успешной проводки. Не определять поток по последнему isActive и человека по изменяемому username.

**Local отличается:** `backend/src/routes/payment.js:118` читает первый X-Forwarded-For, но не подтверждает объект у API. Подставляемый заголовок не заменяет доверенную цепочку proxy. Простая публикация локального файла не является завершённым исправлением. [ЮKassa: входящие уведомления](https://yookassa.ru/developers/using-api/webhooks).

### S-02 — старые подписанные Telegram-данные принимаются без срока

**Production, severity medium, confidence high.** `server/auth-service.js:32–38` после HMAC сразу разбирает user; auth_date не проверяется. `:42` выдаёт JWT на 30 дней. **Предусловие:** ранее полученная действительная подписанная initData конкретного одобренного аккаунта, например из утечки/копирования; бот-токен атакующему не требуется. **Impact:** повторная авторизация этим аккаунтом через длительное время. Admission и deletedAt ограничивают ущерб: отозванный/удалённый аккаунт не получает доступа. **Repro:** fixture-key и auth_date=1, подпись с тестовым ключом; VM production validator принимает user. Реальные подписи/аккаунты не использованы.

Local `backend/src/services/auth.js:37–41` уже проверяет 24 часа, использует timingSafeEqual и JWT 7d; опубликованная версия этого не содержит. В local дополнительно стоит требовать конечное целое auth_date и не принимать слишком будущую дату; это hardening, не доказанная подделка подписи. Исправление — осознанный TTL, freshness и короткий допустимый clock skew, ошибка parse вместо 500; регрессионные фикстуры и подтверждение совпадения source/deployed. [Telegram: проверка initData](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).

### R-01 — тихая потеря записей при плохой сети

**Local и published UI, confidence high.** `app/js/storage.js:33–41`, `:148`, `:194` пишут cache и проглатывают ошибки POST. `app/js/app.js:602–606` сразу открывает «сохранено». `storage.js:243–252` при следующем непустом GET заменяет дневник серверным массивом и выбрасывает локальную неподтверждённую запись. При blocked storage `boot.js:13` оставляет её только в памяти; закрытие WebView уничтожает её. **Предусловие:** API timeout/500, разрыв VPN либо закрытие окна до ответа. **Impact:** личный текст утрачен, экран сообщает успех. `security-quality-repro.cjs` подтвердил loss без сети/БД. Координатор отдельно проверил опубликованную HTML в Chromium/WebKit с перехваченным POST500: UI всё равно показывает «Запись сохранена». Результат `output/app-audit-20261008/browser-results.json`, SHA HTML `ee0d932358d142363bdd16aa024a03dbe7d3d0c9a9885d497c8c758e5e37aea1`; это безопасный браузерный mock, реальные записи на сервере не создавались.

Исправление: запись с client UUID, pending/synced/failed, постоянная очередь повторов там, где доступно, server idempotency; merge по ID, а не замена snapshot; «сохранено на устройстве, ожидает синхронизации» отличается от server ack. Если storage недоступно, сообщить прямо и дождаться server ack перед успехом. Одного catch/toast недостаточно.

### S-03 — кэш личных данных не привязан к аккаунту

**Local privacy severity low (совместное устройство), confidence high.** `storage.js:4–15` использует общие tp_*; `api.js:78–80` logout убирает только JWT. `storage.js:243` сохраняет старый cache при успешном пустом GET нового аккаунта; аналогично диагностике/триггерам/чекинам. **Предусловие:** общий WebView/origin между двумя аккаунтами или выход и другой вход на устройстве. Telegram может разделять контексты в некоторых клиентах; это не гарантия нашего кода. **Impact:** человек видит предыдущие заметки/состояния; старые локальные consent/onboarding тоже могут пропустить новый onboarding, хотя согласие нового аккаунта на сервере отсутствует. **Repro:** тот же offline harness, после записей первого аккаунта новый GET [] оставляет старую запись.

Исправление: ownerId устанавливается по проверенному auth response до чтения cache, namespace + очистка при mismatch/выходе/отзыве, пустой успешный snapshot обнуляет только synced-долю соответствующего owner; pending-доля переносится только своему owner. Все consent-флаги восстанавливаются из серверного состояния, включая false/null. [OWASP: хранение чувствительных данных](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html).

### R-02 — чекин теряет исходные пять шкал и обновления

`storage.js:190–194` отправляет только арифметическое среднее. `:271–283` восстанавливает его сразу в напряжение, тревогу, энергию, безопасность и контакт. У шкал разные направления: одинаковое среднее не является доказанным «верным трендом». `app.js:2083–2086` повторный чекин того же дня меняет только localStorage — серверного update нет. **Confidence high.** После нового входа даже успешное сохранение не восстанавливает исходные ответы. Нужны пять самостоятельных полей, дата/часовой пояс, upsert/версия, прозрачная маркировка исторических усреднённых записей. Не реконструировать отсутствующие показатели как точные.

### P-01 — дневник автоматически передаётся внешнему AI

**Production/local, confidence high, privacy/product finding, не индивидуальное правовое заключение.** `backend/src/routes/ai.js:57–72` и серверный ai.js читают пять заметок и вставляют свободный текст в system prompt. Нет параметра «не использовать дневник». Свободный текст может содержать имена/здоровье/других людей; технического обезличивания нет. Дневниковый текст внутри system role смешивает доверенные правила и недоверенное содержание; prompt injection влияет на ответ, но здесь нет инструментов/чужих данных, поэтому не заявляется захват сервера.

Исправление: явная видимость контекста/выбор записей/отключение; минимизация и отдельный блок пользовательских данных, правила работы с недоверенным содержанием; модель помощи и кризисных сообщений, версия согласий/политики. Текущий system prompt «не ставь диагнозы» — полезная граница, но проверка риска и кризисный маршрут отдельно не реализованы. Vercel участвует в API-передаче: карта получателей должна отражать Beget, Telegram, Vercel и OpenAI по действующим договорам и фактам обработки.

### P-02 — отзыв допуска закрывает экспорт и удаление своих данных

**Production/local, confidence high.** `backend/src/routes/gdpr.js:6,34` защищены общим requireAuth, а он вызывает admissionError. После rejected человеку недоступны ни вход, ни собственный экспорт/удаление. Нужен отдельный authenticated-self маршрут управления данными без club-admission, не доступ к функциям клуба. Текущий экспорт `gdpr.js:8–29` не содержит AI-диалогов, feedback и полного статуса участия; называть его «все мои данные» некорректно.

Удаление немедленно отзывает токен и убирает часть профиля, но `firstName`, `lastName`, `username`, telegramId остаются; это не полное обезличивание. `bot.js:494–519` очищает семь категорий спустя 30 дней, User/Enrollment сохраняет. `backend/scripts/backup-db.sh:3–6` намеренно хранит дампы бессрочно. Нужен согласованный срок/основание каждой категории и backups, процедура восстановления с повторным применением deletion ledger. Фактическая установка этого backup-скрипта, содержимое дампов/выполнение cron не проверены, бессрочные production backups не объявляются установленным фактом.

### H-01 — пользовательский текст рендерится как HTML

**Local, confidence high для DOM injection, attack severity не назначена без межпользовательского пути.** `app.js:309,317,359,1088,1973,1975,2185` вставляют note/sensation/situation в innerHTML. HTML в собственной заметке становится DOM/может запускать обработчик событий. Обычный backend ownership ограничивает запись самим пользователем: не найден путь, где другой участник читает этот текст. В `site/admin.html:713,716,742` ключевые ответы/feedback escaped — контрдоказательство утверждению о захвате админки через отзыв.

Исправление: textContent для свободного текста или единое контекстное экранирование; CSP как дополнительный слой после устранения inline-handler зависимости. JWT в `api.js:9,15` хранится в localStorage, поэтому любой иной будущий XSS имеет серьёзный эффект; хранение токена/данных пересмотреть под Telegram SecureStorage с проверкой версии и безопасным fallback либо серверную сессию. Одна замена хранилища не устраняет DOM injection. [OWASP: frontend security](https://cheatsheetseries.owasp.org/cheatsheets/Web_Frontend_Security_Cheat_Sheet.html).

## Остальные доработки с конкретной пользой

- **Уведомления:** `bot.js:330–365,415` рассылает в 20:00 МСК всем active enrollments и не читает notificationsTime. Два активных зачисления могут дать два сообщения. Send-loop встреч `:392–408` закомментирован. Нужны выбор/пауза/таймзона, дедупликация на user+event, журнал результата, настройки не обещают неисполняемое поведение. Admission gate в запросах уведомлений присутствует.
- **AI надёжность:** ai.js хранит всю историю в одном JSON; parallel read-modify-write способен потерять один из двух ответов. Timeout клиента 60с не отменяет автоматически ответ OpenAI/backend, повтор может дублировать расход/сообщение. Нужны request ID, статус задачи, контроль версии/транзакция, предел контекста, timeout и квоты по пользователю. Числа квоты — предложение, не новое обещание/тариф.
- **История:** UI получает только 90 дневников/реакций и 200 чекинов. Не выдавать ограниченный cache за всю историю. Пагинация/полный серверный экспорт, период на экране и поиск полезнее декоративного счётчика серии.
- **API ограничения:** diary/triggers/checkins GET принимают Number(limit/offset) без query-schema и cap. Поля note/sensations не имеют продуктовых разумных ограничений, хотя Fastify общий body-limit сдерживает объём. Установить лимиты/валидацию/пагинацию, не заявляя уже доказанный массовый DoS.
- **Статистика времени:** local date, серверный timezone и UTC heatmap различаются. Определить Europe/Moscow/таймзону участницы для календарного дня; сверить записи около полуночи. program access уже использует московские сутки и три календарных месяца — полезная реализованная граница.
- **Анкеты:** author ownership есть, но POST допускает произвольный существующий streamId без собственного зачисления и ответы как свободный object. Это риск загрязнения метрик чужого потока, не чтение чужих данных. Проверять принадлежность/фазу/версию анкеты и уникальность user+stream+type в БД.

## Что уже работает и что не следует переделывать вслепую

Оффлайн `backend/scripts/test-club-access.js` прошёл: pending, однократная заявка, admin-only решения, approval, revoke ранее выданного токена, rejected re-entry и защита служебного аккаунта. requireAuth смотрит свежий user/accessStatus на каждом защищённом запросе — закрытие клуба не держится только на клиентском флаге. Личные GET и AI session ownership фильтруют userId; в проверенных маршрутах прямого IDOR-чтения чужого дневника/AI не найдено. Program access отделяет admission и оплату, исторические права и календарный период; не объединять их единым premium-флагом.

Бандл запуска, ранний ready, watchdog, относительный API, no-store и storage fallback уже есть. Их наличие не доказывает стабильность реального Telegram/VPN и успешную синхронизацию. Cron очистки существует — неверно писать «удаления вообще нет»; его полнота, UI и backups остаются вопросом.

## Современный стандарт Telegram и скорости

Актуальная документация Telegram описывает native SecureStorage/DeviceStorage, safeAreaInset/contentSafeAreaInset, изменяемые события viewport/safe area, downloadFile. Клиент сейчас использует CSS env safe-area и 100dvh, но не native content-safe-inset; обновления SDK/разных клиентов нужно проверять, а не автоматически внедрять все методы. Для нашего закрытого дневника полезны безопасный токен, корректная клавиатура/нижняя панель, подтверждение выхода с черновиком и надёжная загрузка экспорта; fullscreen/геолокация/датчики движения не следуют из задачи. [Telegram Mini Apps: design и API](https://core.telegram.org/bots/webapps).

Цели web-производительности: LCP ≤2.5с, INP ≤200мс, CLS ≤0.1 на 75-м перцентиле; это ориентиры браузерного UX, не измеренные показатели приложения и не гарантия скорости auth/API. Для приложения отдельно измерить cold open → auth → diary interactive и процент ошибок по устройству/клиенту/VPN, без заметок/полных initData в телеметрии. Получить реальную iPhone/Android-проверку при плохом соединении, blocked storage, повторном входе и background/resume. [Google web.dev: Web Vitals](https://web.dev/articles/vitals). Сохранение Web Storage не гарантировано при отказе/quota/очистке; серверный ack/очередь — важнее вида localStorage. [MDN: quotas/eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).

## Выполненные безопасные проверки и критерии приёмки

`node backend/scripts/test-club-access.js` — PASS. `node "База знаний/Техническое/Аудит приложения 2026-10-08/security-quality-repro.cjs"` — два подтверждённых regression-сценария (silent loss, cross-account stale cache). `security-production-repro.cjs` — непроверенный webhook достигает mocked enrollment и signed fixture auth_date=1 принимается production validator. Скрипты запускаются из корня, используют только фиктивные данные; production source snapshots нужны последнему скрипту. Это диагностические воспроизведения, не тесты исправленной реализации.

Публикация и фиксы данным аудитом не выполнены.
