# Постепенное обновление Mini App — Implementation Plan

> **For implementers:** Follow the tasks in order, track completion with checkboxes (`- [ ]`), and verify each completed behavior. Use available project tools and skills as needed.

**Goal:** Постепенно сделать закрытое приложение надёжным, понятным и полезным участницам, сохранив записи, программу и природный характер.

**Architecture:** Существующие Mini App, API, бот и Prisma остаются основой. Изменения делятся на небольшие проверяемые выпуски; данные мигрируются с сохранением истории, опубликованные версии сверяются отдельно от локального кода. Продуктовые предложения проходят проверку на реальном сценарии участницы.

**Tech Stack:** HTML/CSS/JavaScript, Telegram Mini Apps SDK, Node.js/Fastify/grammY, Prisma/PostgreSQL, существующие Vercel/Beget и OpenAI gpt-4o-mini.

## Как идём

Один небольшой выпуск → проверка → точная фиксация опубликованной версии → показ результата владельцу → следующий выпуск. Не нужно ждать всех семи этапов, чтобы исправление сохранения принесло пользу. Если обнаружена потеря/искажение данных или обход прав, следующую новую функцию откладываем до устранения.

Для каждого выпуска различать «исправлено локально», «проверено», «опубликовано», «проверено на телефоне». Сборка в WebKit не равна приёмке Telegram на iPhone. Содержимое личных дневников не попадает в логи диагностики. Коммит/push/публикация выполняются в пределах отдельного поручения и действующих правил проекта; общий положительный отзыв не заменяет фиксацию конкретного выпуска.

## Подготовка каждого выпуска

- [ ] Сверить текущие изменения и действующий сервер с аудитом; отделить уже сделанные исправления от новых. Не перезаписывать накопленные работы других задач.
- [ ] Зафиксировать исходную версию, нужную резервную копию, план восстановления и риск миграции. Перед изменением схемы проверить восстановление нужного набора данных.
- [ ] Воспроизвести затрагиваемую проблему на синтетических данных. Нужные автоматические проверки добавлять для потери данных/прав/миграций, а не для каждой простой подписи.
- [ ] Выполнить небольшой законченный участок, повторить его сценарий и обязательные регрессии.
- [ ] Проверить опубликованную версию после фактической публикации; сообщить, что именно стало работать и что ещё не проверено.

Базовые проверки: `node scripts/build-static.mjs`; `scripts/test-app-startup.py`; `scripts/test-club-ui.py`; безопасные audit-repro рядом с отчётом 02. Параметры существующих скриптов сверить перед запуском; действия допуска проверять на фикстурах, не рассылать тестовые уведомления настоящим людям. Аудитные repro демонстрируют старый дефект: после исправления превратить нужные сценарии в проверки ожидаемого безопасного поведения.

## Этап 1. Сохранность записей, повторный вход и защита прав

**Первый видимый выпуск 1А:** запись не исчезает и приложение честно сообщает, где она сохранена. Аккаунт восстанавливается по подтверждённой сервером личности; прежнее согласие и записи не зависят только от локального флага.

**Затрагиваемые файлы:** `app/js/storage.js`, `app/js/api.js`, `app/js/app.js`, `backend/src/routes/auth.js`, `backend/src/services/auth.js`; необходимые стили состояний `app/css/styles.css`. Разделение кэша и очередь синхронизации остаются в storage, транспорт — в api; не переписывать всю навигацию.

- [x] Привязать кэш к userId; очистить чужой активный контекст при смене аккаунта. Для старого кэша без владельца не угадывать принадлежность; определить безопасную миграцию/возможность выгрузки перед очисткой.
- [x] Разделить локальное сохранение и серверное подтверждение; очередь неподтверждённых записей со стабильным clientId, повтором без дублей и слиянием по идентификатору. При необходимости серверная поддержка идемпотентности в маршруте дневника и Prisma.
- [x] Не терять очередь при непустом серверном ответе. Не удалять серверную историю из-за пустого/ошибочного ответа.
- [x] Восстанавливать онбординг из серверного состояния, различать новый аккаунт, ожидание допуска, отказ, временную ошибку и истёкшую сессию.
- [x] Проверить: POST500; обрыв сети; закрытие сразу после записи; повторный вход; повтор доставки; два аккаунта, второй пустой; отсутствие/запрет storage.

**Отдельный срочный выпуск 1Б в том же приоритете:** проверка платёжного webhook и Telegram авторизации. Он не должен ждать нового дизайна. Файлы `backend/src/routes/payment.js`, `backend/src/services/auth.js`, `backend/src/routes/auth.js`; регрессия `backend/src/services/admission.js`.

- [x] Проверять платеж у провайдера и сопоставлять ID, статус, сумму, валюту, получателя, назначение и допустимое состояние зачисления; повтор события не создаёт второй доступ. При невозможности проверки не назначать оплаченные права.
- [x] Проверять свежесть подписанной initData, ограничить сессию, сохранить отзыв токена/допуска. Сначала сравнить локальный и production код: не считать существующую локальную правку опубликованной.
- [x] Проверить поддельное/повторное/чужое платёжное событие, устаревшую подпись, одобренный/ожидающий/отозванный аккаунт. Не проводить настоящую оплату для теста без отдельной необходимости.

**Выход этапа:** нет ложного сообщения об успехе, неподтверждённая запись не пропадает, чужой кэш не показывается, повторный вход не сбрасывает принятые сервером состояния; недействительное событие не меняет права. Белый экран проверяется отдельно по фактическому запуску на телефоне.

## Этап 2. Правильный поток и достоверные наблюдения

**Результат:** выбранный октябрьский поток и весенний архив показывают свои даты/статистику; пять шкал остаются пятью шкалами.

**Файлы:** `app/js/app.js`, `app/js/storage.js`, `app/js/data.js`, `backend/src/routes/checkins.js`, `backend/prisma/schema.prisma`; маршрут собственного доступа/потока `backend/src/routes/me.js` по необходимости.

- [ ] Убрать весенние константы из расчёта пути. Источник периода — выбранный серверный поток, московские даты; состояния до начала/идёт/завершён раздельны.
- [ ] Фильтровать статистику по периоду выбранного потока, не смешивать архив с новым набором.
- [ ] Сохранить каждую шкалу отдельно с понятным направлением. Повторное наблюдение за день обновляет сервер, а не только устройство.
- [ ] Мигрировать старые записи с отметкой «сохранено только среднее», не выдумывая утраченную пятёрку значений.
- [ ] Проверить день до старта, начало, границу московской даты, завершение, архив, отсутствие потока; пять разных значений → сохранение → повторный вход → те же пять.

**Выход этапа:** календарь соответствует выбранной программе, графики не создают ложных наблюдений. Ближайший поток начинается 15 октября по действующим данным: этап имеет практический приоритет до запуска группы, но срок завершения не обещан без оценки реализации.

## Этап 6. Полезные функции по одному сценарию

Выпуски идут отдельно, в указанном порядке; библиотека материалов зависит от утверждения ведущими. Не увеличивать сразу нагрузку сопровождения.

- [ ] **6Б — возвращение к записям:** поиск, фильтр по периоду/контексту, избранное; полный дневник с пагинацией. Хранилище/API/экран истории. Проверить поиск в старых страницах, пустой результат и сохранение избранного между входами.
- [ ] **6В — запись после встречи и собственный шаг (I-030):** несколько согласованных вопросов, выбранное посильное действие и возвращение к результату. Проверить, что запись остаётся личной и ничего не отправляется ведущей автоматически.
- [ ] **6Г — напоминания:** время, частота, пауза и тихий режим; связать настройки с фактическим cron/ботом. Проверить часовой пояс, выключение и отсутствие повторов на тестовых получателях. Не обещать доставку до этой проверки.

Польза проверяется короткими сценариями с добровольными участницами: найти встречу, сделать запись, вернуться к ней, понять приватность. Исследование не проведено этим планом, результаты не выдумывать.
