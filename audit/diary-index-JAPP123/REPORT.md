## Зачем

Запрос `WHERE user_id = ? ORDER BY created_at DESC, id DESC LIMIT 91` соответствует уже существующему API. На искусственной истории из10 120 записей одного владельца прежний план выполнял Seq Scan → Sort → Limit. Новое B-tree `(user_id, created_at DESC, id DESC)` позволяет Index Scan → Limit. Порядок, включая одинаковую дату/ID, сохраняется.

Изменяются только `backend/prisma/schema.prisma` (один @@index) и новая миграция `20261019170000_diary_owner_date_index/migration.sql`. Создание `CONCURRENTLY` выполняется вне транзакции, без IF NOT EXISTS, чтобы одноимённый чужой/невалидный индекс не считался успехом. Ограничения уникальности, строки дневника, auth, API и клиентский код остаются прежними.

## Цена и границы

Индекс требует места на диске и обслуживания при insert/update/delete. На учебной базе его размер около1,125МиБ; накладные расходы записи и размер на рабочем объёме не измерены. Это кандидат улучшения частого чтения последних записей, не обещание ускорения всех запросов.

CONCURRENTLY поддерживает возможность записи при построении индекса по правилам PostgreSQL; параллельная пользовательская запись именно во время построения в этом тесте не запускалась. Полный `prisma migrate deploy` с рабочей историей миграций не проверялся: перед будущим выпуском нужно проверить журнал миграций, отсутствие/состояние одноимённого индекса, диск и режим выполнения вне транзакции. При сбое возможен невалидный индекс — перед повтором проверять его состояние. Никакого автоматического удаления индекса или изменения рабочей базы этот локальный пакет не выполняет.

Официальная основа, проверена19октября: [ORDER BY и LIMIT](https://www.postgresql.org/docs/current/indexes-ordering.html), [CREATE INDEX CONCURRENTLY](https://www.postgresql.org/docs/current/sql-createindex.html). Фактический тест выполнен на установленном PostgreSQL, а не только по документации.

Полный клиентский кэш, число страниц полной истории, схема checkins и физический Telegram в этот пакет не входят. Их улучшение не заявляется.
